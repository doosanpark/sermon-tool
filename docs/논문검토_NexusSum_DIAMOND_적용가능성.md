# 논문 검토 — NexusSum / DIAMOND 를 sermon-tool 에 적용할 수 있는가

- 검토일: 2026-08-30
- 대상: [arXiv:2505.24575](https://arxiv.org/abs/2505.24575) *NexusSum* / [arXiv:2506.02351](https://arxiv.org/abs/2506.02351) *DIAMOND*
- 실측 근거: `data/cache/ZEKoljLiXOw.transcript.json`, `data/markers/ZEKoljLiXOw.json` (78.7분, 전사 600문장 / 14,304자)

## 결론

두 논문의 **메인 파이프라인은 둘 다 이 도구에 필요 없습니다.**
값어치가 있는 건 DIAMOND 의 구조를 **`core/refine.py` 의 경계 미세보정**에 옮기는 한 가지입니다.
그 자리는 지금 사실상 비어 있습니다 — 저장된 실제 영상에서 **보정 규칙 네 개 중 세 개가 한 번도 걸리지 않았습니다.**

| 출처 | 항목 | 판정 |
|---|---|---|
| NexusSum | 계층 청킹 · 다단계 요약 파이프라인 | **필요 없음** |
| NexusSum | Preprocessor 사상 → STT 원문 정제 | **채택 권고** |
| NexusSum | Compressor 길이 제어 (LAR) | 요약 기능 추가 시 |
| DIAMOND | 수치 + LLM 보정을 **성문 1차 검출**에 | **건드리지 말 것** |
| DIAMOND | 같은 구조를 **경계 미세보정**에 | **최우선 권고** |
| DIAMOND | Reflection 사상 → 하이라이트 클립 추천 | 2순위 (새 기능) |

## 1. 실측 — 지금 경계 보정이 이 영상에서 한 일

`core/refine.py` 의 정규식을 실제 전사문에 그대로 돌린 결과.

| 규칙 | 히트 | 결과 경계 | 실제로 일어난 일 |
|---|---:|---:|---|
| 설교 시작 | 4 | 1938.3s | 보정은 됐으나 **3.3초 늦음**. 실제 첫 문장 "이번 시간 하나님 말씀을 같이 보겠습니다"(1935.0s)가 잘림. 히트 4건 중 2건(2443.0 / 3452.6)은 **설교 한복판** |
| 설교 끝 | **0** | 4110.0s | 보정 없음. 성문 블록 끝이 그대로 |
| 축도 시작 | **0** | 4422.0s | 보정 없음. 정형구 7개 전부 실패 |
| 축도 끝 | **0** (히트 6건 전부 창 밖) | 4680.0s | "아멘" 6건이 모두 2046~3437s, 즉 설교 안쪽. `refine_window=150` 밖이라 버려짐 |

`markers/ZEKoljLiXOw.json` 은 `refined: true` 지만, 실제로 보정된 경계는 넷 중 하나뿐입니다.

### 왜 실패했나 (둘 다 정규식으로는 못 막음)

**① 표현이 매번 다름** — 목사님은 "오늘의 본문" 이 아니라 "오늘 주시는 말씀은" 으로 시작하셨습니다.

**② STT 오인식이 정규식을 무력화** — 축도 정형구 3개가 이렇게 어긋났습니다.

```
전사문 4651~4660s (실제 축도 한복판)
  "지금 우리 주위에서 그리스도의 은혜와 / 가난인의 사랑과 / 성경의 교통하심"

refine.py 가 찾던 것
  주 예수 그리스도의 은혜   → "주 예수" 없어서 실패
  하나님의 사랑과           → "가난인의" 로 들려 실패
  성령의 교통하심           → "성경의" 로 들려 실패
```

고린도후서 13:13 이 또박또박 나왔는데도 세 패턴이 전부 빗나갔습니다. 글자 하나만 틀려도 정규식은 죽습니다.

## 2. NexusSum — 계층 파이프라인은 불필요

NexusSum 이 푸는 문제는 "입력이 컨텍스트 창보다 길다" 입니다 (BookSum 평균 입력 158,645 토큰).

- **여기 입력은 설교+축도 전체가 14,304자 ≈ 1.0~1.6만 토큰.** BookSum 의 1/10 수준, 한 번에 들어갑니다.
- 청킹·계층 요약은 순수 오버헤드.
- 설교는 목사님 한 분의 독백 → 간판 기법인 *대사 → 3인칭 서술 변환* 은 변환 대상 자체가 없음.

### 다만 Preprocessor 의 **사상**은 가져올 값어치가 있음 → 자막 정제

논문 ablation 에서 Preprocessor 단독 기여 +2.45 BERTScore (전체 상승분 중 2위).
"요약 전에 입력을 정돈하면 뒤 단계가 다 좋아진다" 는 이야기입니다.

여기서의 대응물은 **구어 정리 + 고유명사 교정**. 이건 요약 이전에 **지금 내보내는 `.srt` 품질 문제**입니다.

```
이 전사문에서 발견된 오인식
  느에미아 / 니에미아  → 느헤미야
  가난인의 사랑        → 하나님의 사랑
  성경의 교통하심      → 성령의 교통하심
```

성경 66권 이름 + 예배 용어 + 교회 이름만 담은 **치환 사전 하나**면 LLM 없이 대부분 잡힙니다.
`core/transcribe.py` 뒤에 한 단계 붙이면 됩니다.

### Compressor 의 길이 제어 (LAR)

주보 문구·유튜브 설명란은 글자 수가 정해져 있는데, LLM 에 "200자로" 라고 하면 잘 안 지킵니다
(논문의 제로샷 LAR 0.2~0.6 → NexusSum 반복 압축으로 ~1.0).
지금은 요약 기능이 없어 해당 없음. **만들게 된다면** 길이 제어는 이 방식을 그대로 쓰는 게 맞습니다.

## 3. DIAMOND — 성문 1차 검출에는 붙이지 말 것

논문 성적표를 그대로 옮기면 오해하기 쉽습니다. DIAMOND 가 보여준 건 **수치 지표(WPA)만 쓰면 F1 42.9% 이던 문제를
LLM 을 얹어 84.8% 로** 올린 것입니다(KBO 경기 5편). 올릴 여지가 두 배 가까이 남아 있었습니다.

- sermon-tool 성문 검출은 **이미 IoU 97.0% / 97.8%** — 남은 여지 3%.
- 이 3% 를 위해 네트워크 의존 · API 키 · 지연 · 환각 위험을 들이는 건 계산이 안 맞습니다.
- 80분 영상 CPU 75초라는 성질도 지켜야 합니다. **`core/voiceprint.py` 검출부는 지금이 정답입니다.**

## 4. DIAMOND — 경계 미세보정에 옮기는 것이 결론 (최우선)

DIAMOND 3단 구조를 한 줄로: **수치 신호가 후보를 좁히고 → LLM 이 그 안에서 문맥으로 고르고 → 규칙이 확정.**

이 도구는 이미 앞 단계를 갖고 있습니다. 성문 유사도가 경계를 ±수십 초로 좁혀 놓았습니다.
비어 있는 건 가운데 단계이고, 지금 그 자리에 정규식이 서 있다가 위처럼 세 번 실패했습니다.

### 구현 모양

1. 1차 경계 ±150초의 STT 문장 60~80개에 번호를 붙임 (2~3천 토큰)
2. LLM 에게 묻는 것은 셋뿐 — **"설교가 실제로 시작하는 문장 번호 / 마무리 기도로 넘어가는 번호 / 축도가 시작하는 번호"**
3. 출력은 **정수 인덱스**. 범위 밖이면 버림

### 이 설계의 좋은 성질

- 출력이 정수 하나라 **환각할 여지가 거의 없고** 검증이 쉽다
- 영상 한 편당 호출 1회, 비용이 작다
- **실패하거나 네트워크가 없으면 지금 정규식 결과로 그대로 떨어진다** — 현재 동작이 하한선이라 후퇴 위험이 없다

## 5. DIAMOND Reflection — 하이라이트 클립 추천 (2순위, 새 기능)

DIAMOND 의 본체는 "긴 녹화에서 순간 K개를 골라 타임코드로 클립을 뽑는다" 입니다.
`marker.clips` 와 `core/cut.py` 가 이미 있어 뼈대는 서 있고, 교회가 원하는 1~3분 숏폼이 이 모양입니다.

"사버메트릭스" 자리에 넣을 수치 신호는 **새 모델 없이 이미 있는 데이터**로 만들 수 있습니다.

- 성문 유사도의 급변
- 발화 밀도 = 세그먼트 글자수 ÷ 초 (평균 4.05초 세그먼트가 이미 있음)
- 강조 직전의 무음 길이 (`bin/models/silero_vad.onnx` 이미 번들)
- 성경 인용 위치 (`\d+장 \d+절` 정규식이 실제로 4건 잡음)
- 같은 구절의 반복

**주의 — 정직하게 적어 둡니다.** DIAMOND 의 WPA 는 *검증된 외부 승률표* 에 근거합니다.
설교에는 그런 근거표가 없어서 위 신호는 전부 손으로 만든 휴리스틱이고,
"통계가 LLM 을 붙잡아 준다" 는 논문의 핵심 주장이 여기선 약해집니다.
그래서 top-K 를 그대로 내보내지 말고 **후보 5~8개를 GUI 에 보여 주고 사람이 고르는** 형태여야 합니다.

## 6. 공통 걸림돌 — LLM 을 어떻게 넣을 것인가

두 논문 다 Mistral-Large 를 A100 4장에 올려 돌렸습니다. 여기서는 불가능합니다.

- 로컬 소형 LLM 은 `CLAUDE.md` 의 **"런타임에 torch 를 쓰지 않는다"**, **"lite 600MB"** 를 정면으로 어깁니다.
  화자 분리를 걷어낸 것과 똑같은 이유로 안 됩니다.
- 현실적인 길은 **API 호출뿐**.
- 그런데 이 프로그램의 강점이 정확히 그 반대편 — 설치하면 그냥 되고, 인터넷 없이도 되고, 돈이 안 듭니다.

**조건: LLM 기능은 전부 기본 꺼짐, 선택 기능.**
설정에 키를 넣은 사람에게만 켜지고, 꺼져 있으면 지금과 100% 똑같이 동작해야 합니다.
`use_voiceprint` 플래그를 다루는 방식 그대로.

## 7. 제안하는 우선순위

1. **보정 정규식 + 자막 치환 사전 보강** (LLM 없이)
   위 실패 네 건은 대부분 패턴 몇 줄과 오인식 치환표로 지금 메울 수 있습니다.
   LLM 을 붙이기 전에 이걸 먼저 해야 "LLM 이 실제로 얼마나 나은가" 를 잴 기준선이 생깁니다.
2. **정답 경계를 손으로 표시한 회귀 세트** (LLM 없이) — 아래 참조
3. **DIAMOND 식 LLM 경계 판정** (선택 기능) — 정규식 폴백 구조로
4. **길이 제어 요약 → 하이라이트 후보 추천** (선택 기능)

## 8. 덧붙임 — 논문에서 가져올 가장 즉각적인 것은 기법이 아님

두 논문 다 "무엇으로 좋아졌다고 말할 것인가" 를 먼저 못 박고 시작합니다.
DIAMOND 는 top-K 에서의 F1 과 전문가 선호도를, NexusSum 은 BERTScore 와 LAR 를 정의해 두고
**각 단계의 기여분을 따로 쟀습니다.** 그래서 "Preprocessor 가 +2.45" 같은 말을 할 수 있습니다.

지금 sermon-tool 의 근거는 영상 2편의 IoU 97.0% / 97.8% 입니다. 좋은 숫자지만
**두 편으로는 어떤 변경이 개선인지 후퇴인지 판단할 수 없습니다.**
위에서 발견한 정규식 실패도 영상 한 편을 들여다봐서야 나왔습니다.

> 손으로 표시한 정답 경계를 가진 영상 10편 + 그걸 돌려 IoU 를 뱉는 스크립트 하나(`selftest.py` 옆).
> 이게 논문 두 편에서 오늘 당장 가져올 수 있는 가장 값어치 있는 것이고,
> 위 판정들도 그게 있어야 비로소 확인됩니다.
