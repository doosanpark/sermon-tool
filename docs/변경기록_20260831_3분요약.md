## 2. 실측으로 얻은 숫자

전부 2026-07-26 설교(ZEKoljLiXOw, 78.7분 / 설교 36.2분 / 전사 551문장)에서 잰 값이다.

### 자를 자리

```
0.8초 이상 쉼  296곳   평균 7초에 한 번 (호흡)
2.0초 이상 쉼   86곳   평균 25초에 한 번 (문단 전환)
```

### 전사문에는 쉼이 없다 ★

```
문장 550개 사이 간격  →  +0.000초 550건. 양수도 음수도 0건.
문장 시작 → 가장 가까운 실제 쉼  중앙값 1.98초 · 최대 49.03초
```

`faster-whisper` 를 `vad_filter=True` 로 돌리면 무음이 잘려 나가고 말만 이어 붙는다.
그래서 문장 경계에서 그냥 자르면 말꼬리가 잘린다.

### 요약 결과

```
압축비 11.8:1 (원본의 8.5%)   조각 15개   평균 11.5초   2분 55초
1차 선정 221.6초 → 목표 180초 대비 +23%  → 덜어내는 단계가 따로 필요
스냅(쉼 맞추기)이 구간을 벌리는 몫  177초 → 210초  (+19%)
```

### 설교 구조

목사님이 대목을 **번호로 선언**하신다. 이 설교에서는 거의 균등하게 놓여 있었다.

```
08:43  "첫 번째에요 문제보다 하나님이 먼저 보이는 기도의 자리였습니다"
12:27  "두 번째입니다 밖에서 안으로 책임의 방향이 바뀌는 기도의 자리였어요"
18:25  "세 번째는 감정보다 말씀이 기준이 되는 기도의 자리입니다"
24:30  "이제 마지막 네 번째입니다 두려움보다 사명이 커지는 기도의 자리였는데요"
31:59  "말씀을 맺으려고 합니다"
```

**주의: 영상 한 편으로 확인한 것이다.** 다른 주에도 이런 구조인지는 확인되지 않았다.
번호 선언이 없으면 개요가 비고 점수만으로 고르게 되어 뼈대가 약해진다.

## 3. 규칙만으로는 왜 안 되는가 (해 보고 안 것)

"대목 선언 지점부터 30초씩 이으면 되지 않나" 를 실제로 만들어 견주었다. **실패했다.**

강해설교는 **선언 → 봉독 → 해설 → 적용** 순서로 간다. 선언 직후 30초는 대부분 봉독이다.

```
[②] 12:28 +33초  (규칙 버전)
  …책임의 방향이 바뀌는 기도의 자리였어요
  제가 6절, 7절을 읽겠습니다 이제 종이 주의 종들인 이스라엘 자손을
  위하여 주야로 기도하오며 …                    ← 30초 중 25초가 봉독
```

6조각 버전은 "제목 넷 + 봉독" 만 남고 해설이 한 마디도 안 들어갔다.
→ **내용을 읽고 골라야 한다.** 이것이 임베딩·AI 를 넣은 이유다.

## 4. 문장을 고르는 세 단계

DIAMOND(arXiv:2506.02351)의 구조를 그대로 옮겼다.

| 단계 | 무엇을 보나 | 크기·속도 | 논문에서 |
|---|---|---|---|
| 규칙 | 낱말 | 0 · 즉시 | Preparation |
| 임베딩 | 뜻 — 설교 전체를 대표하는가 | 120MB · 몇 초 | Preparation |
| 로컬 LLM | 문맥 — 후보 중 무엇을 남길까 | 2GB · 1~3분 | Decision |
| 편집기 | 사람이 확정 | — | Reflection |

**어느 하나가 없거나 죽어도 앞 단계 결과가 그대로 남는다.**
`selftest.py` 의 `check_stages()` 가 이걸 지킨다.

### 규칙이 부족한 증거

규칙이 고른 것과, 사람이 전사문을 읽고 고른 것의 겹침이 **19%** 였다.

```
규칙이 놓친 것 : "그의 기도를 보면 그의 삶의 구조가 보여요"   ← 설교의 명제
규칙이 넣은 것 : "니에미아 1장 오늘 본문 5절부터 11절까지 말씀입니다"  ← 그냥 안내
```

낱말만 보기 때문이다. 임베딩은 뜻을 보므로 이 자리를 메운다.

### LLM 에게 551문장을 다 주지 않는다

점수 상위 90개만 넘겨 입력을 **1.5만 → 3천 토큰**으로 줄인다(`llm_candidates`).
대목 선언은 점수와 무관하게 후보에 넣는다 — 뼈대가 후보에 없으면 LLM 도 살릴 수 없다.
답은 **문장 번호 정수뿐**이라 지어낼 여지가 거의 없고, 범위를 벗어나면 버린다.

## 5. 세로 화면은 잘라내기가 아니라 짜맞추기

원본은 고정 카메라 한 대로 찍은 **1280×720 · 30fps** 다.

9:16 으로 가운데를 잘라내면 폭이 **405픽셀**만 남아 오른쪽 설교 제목 화면과
왼쪽 십자가가 통째로 날아간다. 그래서 목사님만 크게 잡아 가운데 두고,
제목은 화면에서 오려내는 대신 `marker.sermon_title` 의 글자로 위에 얹는다.

```
1080x1920 화면 나누기
     0 ~  330   제목 + 본문 성구
   330 ~ 1470   영상 (1080x1140)
  1470 ~ 1920   자막
```

크롭 자리는 **비율**로 잡는다(`shorts_center_x` .44 / `shorts_center_y` .61 / `shorts_zoom` .515).
원본을 720p 로 받든 1080p 로 받든 같은 구도가 나와야 하기 때문이다.
고정 카메라라 한 번 맞춰 두면 계속 쓴다.

## 6. llama.cpp 실행파일 — 어느 판을 넣었나

받아 둔 릴리스 5종 중 **`win-cpu-x64` 하나**를 골랐다.

| 판 | 판단 |
|---|---|
| `cpu-x64` | **넣음.** CPU 세대별 DLL 14개가 실행 중에 골라 불린다 |
| `cuda-12.4` / `cuda-13.3` | 뺌. 397MB. "CUDA 없는 PC에서 동작" 원칙에 어긋난다 |
| `vulkan-x64` | 뺌. GPU 있으면 빠르지만 55MB 더 크고 드라이버를 탄다 |
| `cpu-arm64` | 뺌. ARM 윈도우도 x64 를 에뮬레이션으로 돌린다 |

필요한 파일은 `llama-server.exe` 의 **PE 가져오기 표를 직접 뜯어** 정했다.

```
가져오기 연쇄 7개                       23.15MB
+ ggml-cpu-*.dll 14개 (실행 중 선택)     17.4MB
= 40.5MB   (zip 전체는 45.9MB)
```

`bin/llama/` 에 따로 둔다. DLL 이 스물몇 개라 ffmpeg 옆에 흩뿌리면 알아볼 수 없고,
윈도우는 실행파일 옆의 DLL 을 먼저 찾으므로 한 폴더에 모여 있어야 한다.
빌드는 `bin/` 을 통째로 묶으므로 자동으로 들어간다.

## 7. 만들면서 잡은 버그

### 눈금이 33초 거짓말했다 ★

[이전 작업 불러오기] 로 돌아오면 눈금이 "2분 22초" 라고 떴는데 실제로 나오는
영상은 2분 55초였다. 불러올 때 쉼을 다시 찾지 않아, 스냅으로 벌어지는 몫을
빼고 세고 있었다.

**고침**: 길이는 반드시 `highlight.runs(marks, snap)` 한 곳으로만 센다.
불러올 때도 쉼을 찾는다 — 36분치가 0.7초밖에 안 걸린다.

### 자막이 화면 위에 거대하게 떴다

`ffmpeg` 의 `subtitles` 필터에 `.srt` 를 그냥 주면 libass 가 `PlayResY` 를 288 로
가정하고 영상 높이(1920)에 맞춰 **6.7배**로 늘린다. FontSize 52 가 350픽셀이 되고
MarginV 170 이 1130 이 되어 자막이 위로 튀어 올라간다.

**고침**: ASS 로 만들어 `PlayResX/Y` 를 실제 크기로 적는다(`shorts.srt_to_ass`).

### 컷을 가장 가까운 쉼에 붙이면 첫 마디가 잘린다

규칙만으로 자른 시험판에서 "두 번째입니다" 가 1초 차이로 날아갔다.

**고침**: 시작은 **앞쪽** 쉼으로 당기고, 끝은 **뒤쪽** 쉼으로 민다.

### 자막 만드는 35분 동안 아무것도 안 찍혔다

`transcribe_range` 가 35.2분을 한 번에 넘기고 결과를 다 받을 때까지 조용했다.
CPU 에서 20~60분이 걸리는데 진행 표시가 없어 **멈춘 줄 알았다는 신고**가 있었다.

**고침**: faster-whisper 의 제너레이터를 받는 족족 진행률을 찍는다.

### 작업 중에 만진 편집이 소리 없이 사라졌다 ★

`_set_busy` 가 버튼만 잠그고 `range_bar`·`zoom_bar`·목록은 안 잠갔다.
작업이 끝나면 `_apply_marker` 가 구간을 통째로 새로 넣으므로,
도는 중에 손잡이를 끌면 그 편집이 전부 버려졌다.

**고침**: 막대·목록·버튼 9곳을 함께 잠근다. `guitest.py` 가 검사한다.

### 마커가 요약을 담고도 "판 2" 라고 우겼다

`Marker.load` 가 파일에 적힌 판 번호를 그대로 들고 있었다.
**고침**: `save()` 가 저장하는 순간 `SCHEMA_VERSION` 을 다시 찍는다.

### 성경책 이름 오인식

본문 표기가 "느에미아 1:5-11" 로 화면에 박혔다. 태우면 되돌릴 수 없다.
글자째로 견주면 "느헤미야" 와 반도 안 닮은 것으로 나온다.

**고침**: **자모로 풀어** 견준다(`export.fix_book`). '헤'와 '에'는 초성 하나,
'야'와 '아'는 중성 하나 차이다. 8개 중 6개가 같아진다.

## 7-2. 모델을 받은 뒤 다시 잰 것 (같은 날 저녁)

"툴이 만든 요약보다 사람이 고른 게 낫다" 는 말을 듣고, 사람이 고른 것을
정답지 삼아 재 봤다. 세 가지가 나왔다.

### 임베딩 대표성을 잘못 재고 있었다 ★

평균 방향과의 코사인을 썼는데, 문장 벡터가 한 방향으로 쏠려 있어(anisotropy)
값이 전부 **0.853~0.944** 안에 몰린다. 그 상태로는 "중요한가" 가 아니라
"흔한가" 를 재게 된다.

```
평균 방향 상위   "그 말씀을 붙잡습니다" · "이 표현을 가지고 기도합니다"
                (짧은 상투구만 올라온다)
쏠림 제거 상위   "기도가 어떻게 우리의 삶의 구조를 다시 세우는지"
                "기도가 삶의 제일 중요한 틀이에요"
                (설교의 명제가 올라온다)
```

**고침**: 평균을 빼고 제1주성분을 걷어낸 뒤(all-but-the-top) 서로간 유사도로
잰다(`embed.importance`). 되풀이해 말한 생각일수록 여러 문장과 통해 위로 온다.

### 본문 안내가 요약에 들어갔다

"니에미아 1장 오늘 본문 5절부터 11절까지 말씀입니다" 는 내용이 아니라 안내인데,
되풀이되는 낱말 때문에 점수가 높았다. `_ANNOUNCE` 로 걸러 낸다.

### 요약이 뒤로 쏠렸다

구획마다 알아서 고르게 두니 긴 대목에 시간이 몰렸다. 구획 수로 나눈 몫을
각자 채우게 고쳤다. 그런데 **마지막 대목의 구획을 설교 끝까지 뻗게 두는 바람에
맺음말과 마지막 권면이 0초**가 되는 회귀를 한 번 만들었다.
구획이 서로 겹치지 않게 잘라 고쳤다.

### 잰 값

| | 고치기 전 | 고친 뒤 (규칙만) | 고친 뒤 (＋임베딩) |
|---|---|---|---|
| 구획 균등도 | 0.63 | 0.92 | **0.95** |
| 안내·봉독이 섞인 수 | 1 | 0 | **0** |
| 사람 선택과 F1 | 24.7 | 27.6 | **28.6** |

> **F1 숫자를 너무 믿지 말 것.** 정답지가 사람 한 명의 선택 하나뿐이다.
> 3분 요약은 정답이 여러 개인 문제라, 좋은 문장을 골라도 정답지에 없으면
> 점수가 깎인다. 실제로 임베딩이 새로 넣은
> "기도는 우리의 시선이 향하는 곳을 바꿔놓는 자리입니다" 는 좋은 문장인데
> 정답지에 없어 오답으로 잡혔다.
> **균등도와 안내·봉독 수**가 취향을 타지 않아 더 믿을 만하다.

## 7-3. AI 를 처음 돌려 보고 잡은 것

받아 둔 Qwen3-4B 로 [요약 골라줘] 를 눌렀더니 "뜻으로 다시 매긴 문장 459개"
에서 멈춘 것처럼 보였다. 원인 둘.

### Qwen3 는 생각을 먼저 길게 쓴다 ★

Qwen3 계열은 기본으로 `<think>…</think>` 를 길게 쓴 뒤에야 답을 낸다.
우리가 원하는 답은 숫자 배열 한 줄이라 그 생각이 전부 낭비이고,
CPU 에서는 그 낭비가 몇 분이 된다. `max_tokens` 를 생각으로 다 써 버리면
답이 아예 안 나올 수도 있다.

**고침**: Qwen 이 정한 신호 `/no_think` 를 붙이고 `chat_template_kwargs` 로도
꺼 달라고 알린다. 둘 다 모르는 모델이면 그냥 무시된다.
그래도 생각을 쓰면 `<think>…</think>` 를 떼어 낸다.

### 또 조용했다

응답을 통째로 기다리느라 몇 분간 아무것도 안 찍혔다.
**자막에서 겪은 것과 똑같은 실수를 같은 날 두 번 했다.**

**고침**: 흘려받으며(`stream`) 5초마다 진행을 찍는다.

```
[AI] 후보 90문장을 넘깁니다 (약 1500토큰)
```

## 7-4. 자막이 깜빡였다

"음성 안 나오는 자막이 잠깐 나왔다 사라지고 해서 눈이 아프다" 는 말을 듣고 셌다.

```
자막 84줄 중 22줄(26%)이 0.5초 미만 · 그중 17줄이 정확히 0.20초
```

0.20초는 `pauses.snap_start` 가 컷 앞에 두는 여백과 **정확히 같은 값**이다.
말이 다시 시작되기 0.2초 전에서 자르는데, 전사문 문장은 빈틈없이 이어져 있어서
그 0.2초에 앞 문장의 꼬리가 걸린다. 자막을 "조금이라도 겹치면 넣는" 방식이라
그 꼬리가 0.2초짜리 자막이 됐다. 이음매가 스무 곳이니 스무 번 깜빡인다.

**고침**: `build_srt` 에 두 가지 기준을 둔다. 값은 실측으로 골랐다.

| 기준 | 줄 | 깜빡임 | 소리 덮는 비율 | 못 읽을 만큼 빠른 줄 |
|---|---|---|---|---|
| 거르지 않음 | 84 | 22 | 100% | 28 |
| share 0.5 | 52 | 0 | 90% | 0 |
| **cue 1.0 · share 0.3** | **55** | **0** | **93%** | **0** |

세게 거르면 깜빡임은 없어지지만 **소리는 나는데 자막이 없는 대목**이 생긴다.
그 둘을 같이 보고 고른 값이다.

### 곁다리 — 조각이 토막 나 있었다

같이 재보니 조각 22개 중 4개가 5초 미만이고 가장 짧은 것이 2초였다.
`fit_to_target` 이 길이를 맞추느라 문장을 하나씩 빼는데, 그게 이어져 있던 조각의
한가운데면 조각이 둘로 쪼개진다. `drop_slivers` 로 4.5초 미만을 뺀다
(대목 선언이 든 조각은 남긴다). 조각 22 → 20개, 평균 8.5 → 9.0초.

## 8. 되돌리면 안 되는 것

1. **요약 선택을 `marker.clips` 에 넣지 말 것.** `ranges()` 는 `clips` 가 비어 있지
   않으면 그걸 그대로 돌려주고 `export` 가 그걸로 설교 영상을 만든다. 요약 조각을
   넣으면 [설교 영상 만들기] 가 조각 열댓 개를 이어붙인 영상을 뱉는다.
   요약은 `marker.summary_picks` 에 따로 둔다.
2. **길이를 두 곳에서 세지 말 것.** 화면과 결과가 갈라진다.
3. **편집을 타임라인 막대로 되돌리지 말 것.** 자막을 읽으며 문장을 켜고 끄는 방식은
   교회용 클립 도구들이 공통으로 도달한 결론이다. 초 단위를 다루게 하는 순간
   이 화면은 편집 프로그램이 되고, 쓰시는 분들이 손을 못 댄다.
4. **오래 걸리는 일에서 진행 표시를 빼지 말 것.** 조용하면 멈춘 줄 안다.

## 10. 정정 — DIAMOND 수치 (2026-09-01)

이 작업 중에 내가 DIAMOND 논문 성적을 **F1 0.673 → 0.765 / 0.793** 으로 적었다.
